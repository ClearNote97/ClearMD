# ADR-0026: The presenter and the first GUI (ttkbootstrap)

- **Status:** proposed
- **Date:** 2026-10-27
- **Refines:** ADR-0001 (presenter + GUIs), ADR-0003 (the three toolkits), ADR-0008 (GUI libraries in the
  container), ADR-0012 (settings), ADR-0013 (non-technical users first), ADR-0016 (where results go).

## Context

Features 001–004 built the core and the CLI. ADR-0001 promised the same app in three GUI toolkits that share
one presenter, and `spec/contracts/ux.md` says what every GUI must do. The first GUI is the cheapest one,
ttkbootstrap (tkinter with themes), so the presenter is designed against a real window before PySide6 and
flet. The users are not technical: the window must never freeze, never surprise and always say in plain words
what happened and what to do. The author tries the app only as a packaged executable (feature 006); until
then, the GUI is shown as screenshots in `docs/`.

## Decision

### The presenter (`frontend/presenter/`, standard library only)

- **Model-View-Presenter, passive view.** The presenter owns the state and every text; a view only draws what
  it is given and forwards the user's intents. The view is a `Protocol` (`show_state`, `show_inputs`,
  `show_plan`, `show_progress`, `show_result`, `ask`…), so each toolkit implements it and the presenter is
  tested with a fake view, without a display.
- **One state at a time**, the seven of the contract: Ready, Analyzing, Waiting for your decision,
  Converting, Finished, Finished with problems, Cancelled. Each state says which actions are enabled.
- **Never on the UI thread:** planning and converting run in a worker thread that talks to `backend/api`;
  its events reach the presenter through a `schedule(callback)` the view provides (tk: `after`), so the
  presenter only changes state on the UI thread. Cancel sets the batch's `CancelToken`.
- **Every text from the catalogs** (ADR-0012), including rejections through `services/rejections` (UX §3),
  so the three GUIs say exactly the same.
- **Imports:** `backend.api`, `backend.schemas`, `i18n` and the standard library only (an architecture rule).

### The ttkbootstrap GUI (`frontend/ttk/`)

- `ttkbootstrap` (MIT) for the themes: a light and a dark theme, following the system by default (setting
  `theme`). **The system theme is detected by ClearMD's own code** (Windows registry, macOS `defaults`, Linux
  `gsettings`; light when unknown), with no dependency (the author's choice).
- **Drag and drop with `tkinterdnd2`** (MIT, it bundles the tkdnd extension for each system; the author's
  choice) next to **Add files** and **Add folder** (UX §5).
- One window: the inputs and the output choice, the plan to review and confirm, the progress with Cancel, the
  result with **Open results folder**; the help ("?"), the welcome (three steps, "Don't show again") and the
  settings window (the settings of ADR-0012 and **Restore defaults**) as dialogs.
- Layout constants in one place: an 8 px grid, body text 14 px, one primary action per screen.
- Started with `clearmd-ttk` (a GUI script: no console window on Windows).

### Settings the GUIs write

- The GUIs **write** `settings.toml` (until now only read): atomically, keeping only known keys. One new key,
  `last_output_folder` (empty: next to the originals), remembers the folder the user picked (ADR-0016).

### What waits for feature 006

- The **splash** while a packaged executable unpacks is PyInstaller's own (its bootloader shows it before
  Python starts): the window itself appears in well under a second.
- Accessibility names: Tk exposes none to screen readers; the contract's "where the toolkit exposes them"
  applies. PySide6 (007) does.

### Development

- The container gets Tk, a virtual display (`xvfb`) and fonts (ADR-0008, in this GUI's phase). GUI tests run
  under `xvfb`; screenshots of every screen, light and dark, English and Spanish, are generated by a script
  and committed under `docs/screenshots/005/`.

## Consequences

- **Gains:** the interaction logic is written and tested once, without a display; PySide6 and flet will only
  draw. The first GUI ships with every promise of the UX contract that Tk can keep.
- **Costs:** a presenter protocol to keep stable across three toolkits; tkinterdnd2's native binaries in the
  executable; the screenshots must be regenerated when a screen changes.

## Alternatives considered

- **Logic inside the ttk views:** faster now, duplicated twice later (ADR-0001). Rejected.
- **No drag and drop in ttk:** fewer binaries; the author chose the convenience.
- **`darkdetect` for the system theme:** the same work, but unmaintained since 2022. Rejected (the author's
  choice).
- **Viewing the GUI through WSLg:** not needed: the author tries the packaged app; screenshots meanwhile.
